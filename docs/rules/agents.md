# Роли субагентов

## 1. Общие правила

- Субагент получает самодостаточный prompt: цель, пути, границы, критерии.
- Субагент читает `AGENTS.md`, `docs/rules/` и профильную спеку до начала работы.
- Субагент не получает секреты и не читает `.env`.
- Субагент не меняет версию, origin, теги и не выполняет push.
- Субагент не добавляет новые инструменты и зависимости без решения архитектора.
- Субагент возвращает: что сделано, какие файлы изменены, чем проверено, какие риски остались.

## 2. Роли

| Роль | Ответственность | Не делает |
|---|---|---|
| `owner` | Приоритеты, приёмка, версия и тег | Не пишет код вместо исполнителей |
| `architect` | Структура, правила, спеки, ADR, ревизия | Не пишет реализацию |
| `data-engineer` | `core/etl`, dbt-модели, ClickHouse SQL, DAG | Не меняет инфраструктуру и секреты |
| `devops` | Compose, окружения, CI, секреты, бэкапы, runbook | Не меняет модель данных |
| `reviewer` | Код, DAG, документы и ссылки; проверка перед версией | Не правит код, не ревьюит каждый коммит |

### `owner`

Родительская роль, не субагент. Держит контекст, ставит задачи, принимает результат, меняет версию и ставит тег. Не переписывает архитектуру в одиночку и не подменяет исполнителей.

### `architect`

Когда: новая структура, правило, спека, конфликт решений.

Границы: только документация и решения. Код не пишет. Может предложить минимальный пример, если без него решение не проверить.

### `data-engineer`

Когда: реализация ingestion, dbt staging/marts, DAG, схема ClickHouse.

Вход: утверждённая спека, путь к целевому компоненту, критерии.

Границы: не трогает `docker`, `.env`, origin, CI. Не придумывает имена слоёв без решения.

### `devops`

Когда: compose, окружения, CI/CD, секреты, бэкапы, восстановление.

Вход: `SPEC-002` и `docs/rules/environment.md`, список сервисов, критерии.

Границы: не меняет Python-код, dbt-модели и бизнес-логику. Реальные креды не коммитит и не печатает.

### `reviewer`

Когда: при смене версии, перед release-коммитом и тегом. PR и merge пока не используются, поэтому reviewer не вызывается на каждый коммит.

Вход: diff с прошлой версии, спека, правила, критерии приёмки, `node tools/check-docs.mjs --strict`.

Границы: read-only. Проверяет код, DAG, документы и ссылки. Возвращает замечания по серьёзности, не правит файлы. Для независимости запускается как fresh `subagent`, а не `subagent_fork`.

## 3. Когда кого звать

| Задача | Роль |
|---|---|
| Новая структура или правило | `architect` |
| Первый ETL-пайплайн | `data-engineer` |
| Compose для Comlink и ClickHouse | `devops` |
| Проверка перед сменой версии | `reviewer` |
| Конфликт между компонентами | `architect` |
| Версия и тег | `owner` |

## 4. Шаблон prompt

```text
Ты <роль> в репозитории E:\work\ai\swgoh-dlh.

Прочитай:
- AGENTS.md
- docs/rules/<профильные правила>
- docs/specs/<спека>

Задача:
<одна конкретная задача>

Границы:
- <что можно менять>
- <что нельзя менять>

Проверка:
- node tools/check-docs.mjs --strict
- <профильная проверка>

Верни:
- что сделано;
- изменённые файлы;
- чем проверено;
- что осталось и какие риски.
```

## 5. Handoff

```text
owner → architect → owner принимает решение
owner → devops / data-engineer → reviewer → owner → версия и тег
```

- Owner ставит задачу и принимает результат.
- Архитектор фиксирует решение и критерии.
- Исполнитель реализует в границах спеки.
- Reviewer проверяет только при смене версии.
- Owner меняет версию и ставит тег.

## 6. Запреты

- Два субагента одновременно пишут в один файл.
- Субагент меняет версию, тег или origin.
- Субагент коммитит `.env`, ключи или ally code.
- Reviewer правит код вместо замечаний.
- Reviewer ревьюит каждый коммит вместо границы версии.
- Роль без критерия приёмки.
